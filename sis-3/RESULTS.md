# SIS-3 — Результаты и объяснение

## Что меряли

- **База:** каталог товаров, 1 млн товаров, 100 категорий с перекосом (большая категория ≈ 10% товаров, маленькая ≈ 0.6%), 3 млн событий в `outbox`.
- **Нагрузка:** чтения при 500 / 1000 / 2000 RPS плюс всегда 20 RPS записи. До базы доходит ~1000 RPS, потому что перед ней стоит кэш из SIS-2.
- **Смесь чтений:** 60% карточка товара (`get`), 25% страница категории (`list_category`), 15% фильтр по категории и цене (`list_filter`).
- **Цель из SIS-1:** p99 < 80 мс.
- **Метод:** каждый этап начинается с чистой базы и добавляет одно изменение. Запросы уходят строго по расписанию, и время считается от момента, когда запрос *должен был* уйти, поэтому очередь к перегруженной базе видна в p99.
- **Таймаут:** запрос дольше 1 с считается ошибкой.

## 1. Индексы — главный выигрыш

### Результат

| | До | После |
|---|---|---|
| `list_filter` в EXPLAIN | 117 мс, 23 620 страниц | **0.24 мс, 45 страниц** |
| `list_category` (маленькая категория) | 0.6 мс, отбросил 3 431 строку | **0.08 мс**, отбросил 0 |
| запрос воркера `outbox` | 52 мс, перебор 3 млн строк | **0.008 мс** |
| p99 всех запросов при 2000 RPS | ~1000 мс, 12 519 ошибок | **≤ 2.9 мс, 0 ошибок** |

### Объяснение

- **Почему было медленно.** Индекса по категории и цене не было. Postgres шёл по всем товарам подряд (по первичному ключу) и у каждого проверял категорию и цену. Подходящих товаров всего ~40 на миллион, поэтому он перебрал почти всю таблицу: ~1 млн выброшенных строк ради 20 нужных.
- **Почему стало быстро.** Добавили индекс `(category_id, price)`. Postgres сразу прыгает к «категория 100, цена 100», читает до «цена 110», находит ровно 39 строк и сортирует только их. Работы стало в ~500 раз меньше.
- **Правило составного индекса:** сначала колонка с `=` (категория), потом колонка с диапазоном или сортировкой (цена, id).
- **`WHERE status = 'active'` (partial-индекс).** Удалённые товары покупатель не видит, поэтому их нет и в индексе, и он меньше.
- **Почему ускорился даже `get`, хотя его план не менялся.** Без индексов медленные фильтры занимали все 80 соединений, и быстрые запросы по id стояли за ними в очереди, отсюда ~1 с. Индексы освободили соединения, и разгрузилась вся база. Один плохой запрос тормозит всю базу.
- **Почему у большой категории план не поменялся.** В ней 10% всех товаров, поэтому 20 нужных находятся по первичному ключу уже через 335 строк. Это так же дёшево, как открыть индекс, и планировщик выбирает по стоимости.
- **Цена индексов.** Запись стала трогать больше страниц (`dirtied` 4 → 8). UPDATE меняет цену, а цена теперь входит в индекс, поэтому Postgres обновляет все 4 индекса таблицы. При 20 записях в секунду на p99 это не видно (3.5 мс), но при частой записи каждый индекс должен себя оправдывать.

## 2. Партиционирование `outbox`

### Результат

| | Обычная таблица | Партиции по месяцам |
|---|---|---|
| удалить самый старый месяц | `DELETE` — **387 мс** | `DROP TABLE` — **0.66 мс** |
| запрос воркера «события за 7 дней» | одна большая таблица | `Subplans Removed: 3`: старые месяцы не открываются |
| p99 чтений и записи под нагрузкой | 1.4–4.6 мс | 1.4–5.2 мс (без изменений) |

### Объяснение

- **Что сделали.** `outbox` (журнал событий «товар изменился») разрезали на таблицы по месяцам: `outbox_2026_08`, `_09` … `2027_01`.
- **Почему удаление в ~600 раз быстрее.**
  - `DELETE` ищет и удаляет каждую строку по одной и оставляет мусор для VACUUM. Чем больше данных, тем дольше.
  - `DROP` просто удаляет файл партиции, и его время от объёма не зависит.
- **Pruning.** Воркер ищет события за последние 7 дней. Postgres сам понял, что они могут лежать только в свежих партициях, и 3 старые даже не открывал.
- **Почему чтения товаров не ускорились — и так и должно быть.** Мы резали `outbox`, а не `products`.
- **Почему не резали `products`.** Товары ищут по `id`. Если резать их по категории, поиск по id пришлось бы делать во всех партициях. Миллион строк для Postgres — немного.
- **Правило Postgres.** Первичный ключ партиционированной таблицы обязан включать колонку, по которой режем, поэтому PK стал `(id, created_at)`.

## 3. PgBouncer (пул соединений)

### Результат

| Тест | Соединений у клиента | Соединений у Postgres | p99 `get` | Ошибки |
|---|---|---|---|---|
| напрямую | 85 | 85 | 1.4–2.2 мс | 0 |
| PgBouncer, 500 RPS | 85 | **5** | 1.8 мс | 0 |
| PgBouncer, 1000 RPS | 85 | **7** | 1.1 мс | 0 |
| PgBouncer, 2000 RPS | 85 | **13** | 1.4 мс | 0 |
| **300 клиентов напрямую** | 300 | — | — | `sorry, too many clients already` |
| **300 клиентов через PgBouncer** | 305 | **14** | 1.1 мс | **0** |

### Объяснение

- **Проблема.** Каждое соединение с Postgres — отдельный процесс, а лимит `max_connections = 100`. 300 клиентов напрямую получают ошибку.
- **Как работает PgBouncer.** В режиме `transaction` он выдаёт настоящее соединение клиенту только на время одной транзакции, потом отдаёт следующему. Если все 20 соединений заняты, клиент ждёт в очереди, а не получает ошибку.
- **Закон Литтла:** нужно соединений = RPS × время запроса = 1000 × ~1 мс ≈ 1–2. Поэтому соединений у Postgres растёт с нагрузкой (5 → 7 → 13), а не с числом клиентов: 85 клиентов дают 13 соединений, 300 клиентов — 14.
- **Запросы PgBouncer не ускоряет:** p99 такой же, как напрямую. Его выигрыш в другом: сотни клиентов помещаются в несколько соединений, и база не падает.
- **Почему пул 20, а не 300.** Больше 100 соединений Postgres не даст. А 300 одновременных запросов на 12 потоках CPU только мешают друг другу. Маленький пул с очередью работает быстрее.

## 4. Read replica

### Результат

| RPS | `get` p99 | `list_filter` p99 | `write` p99 | Ошибки | Соединений у primary |
|---|---|---|---|---|---|
| 500 | 1.4 мс | 3.3 мс | 3.1 мс | 0 | **1** |
| 1000 | 1.4 мс | 2.9 мс | 2.8 мс | 0 | **1** |
| 2000 | 1.4 мс | 2.9 мс | 3.7 мс | 0 | **1** |

| Лаг реплики | Медиана | Максимум |
|---|---|---|
| во время массовой загрузки (1 млн товаров + 3 млн событий) | 39–92 мс | **222 мс** |
| под обычной нагрузкой | **0.7 мс** | 1.6 мс |

### Объяснение

- **Что сделали.** Подняли копию базы только для чтения (`pg_basebackup`, асинхронная потоковая репликация). Чтения идут на реплику, запись — на primary.
- **Выигрыш.** У primary осталось 1 соединение, только под запись. Раньше на нём было 13. Primary больше не занят чтениями, которых в ~500 раз больше, чем записей.
- **Скорость чтения такая же**, как с primary. На одной машине у реплики тот же CPU и диск, поэтому мощности она здесь не добавляет. На отдельном сервере добавила бы.
- **Цена — лаг.** Реплика асинхронная: primary не ждёт её, и данные на ней отстают. Лаг — это распределение, а не одно число: 0.7 мс в обычном режиме и до 222 мс при массовой записи.
- **Что можно читать с реплики:**
  - карточку, каталог, фильтр — можно: цена со старостью в миллисекунды для каталога допустима;
  - ответ после сохранения и проверку перед записью — нельзя, их читаем с primary.
- **RPO и RTO:**
  - **RPO** (сколько данных можно потерять) ≈ лаг, то есть меньше 1 мс в обычном режиме.
  - **RTO** (за сколько поднимемся) — минуты: автоматического переключения нет, реплику переводим в primary вручную.
- **Ловушка.** `now() - pg_last_xact_replay_timestamp()` на реплике показал 18 с, но это не лаг: это время с последней записи, а запись просто кончилась. Настоящий лаг — `replay_lag` на primary, он в тот момент был 0.7 мс.

## Коротко: что дал каждый шаг

| Шаг | Что дал | Чего не дал |
|---|---|---|
| Индексы | p99 с ~1000 мс до ≤ 5 мс, 0 ошибок вместо 12 519 | бесплатными не были: запись трогает больше страниц |
| Партиции | удаление старого месяца 387 → 0.66 мс, воркер читает только свежие партиции | чтения товаров не ускорили (так и задумано) |
| PgBouncer | 85 → 5–13 соединений у базы, 300 клиентов работают вместо ошибки | запросы не ускорил |
| Реплика | все чтения ушли с primary (1 соединение вместо 13) | на одной машине мощности не прибавила; цена — лаг до 222 мс при массовой записи |

## Ограничения

- Всё работает на одной машине (12 потоков, 15 ГБ RAM): primary, реплика, PgBouncer и генератор нагрузки делят один CPU и один диск.
- Генератор нагрузки на Python держит расписание до ~2000 RPS, поэтому выше не мерили.
- Меряли SQL напрямую, без HTTP API и Redis из SIS-2.
- Настройки Postgres оставили по умолчанию, чтобы выигрыш каждого шага шёл только от одного изменения.
