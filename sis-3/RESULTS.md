# SIS-3 — Результаты и объяснение

Документ идёт по пунктам задания, в том же порядке.

## Что меряли

- **База:** каталог товаров, 1 млн товаров, 100 категорий с перекосом (большая категория ≈ 10% товаров, маленькая ≈ 0.6%), 3 млн событий в `outbox` за 90 дней.
- **Нагрузка:** чтения при 500 / 1000 / 2000 RPS плюс 20 RPS записи. До базы доходит ~1000 RPS, потому что перед ней стоит кэш из SIS-2.
- **Смесь чтений:** 60% карточка товара (`get`), 25% страница категории (`list_category`), 15% фильтр по категории и цене (`list_filter`).
- **Цель из SIS-1:** p99 < 80 мс.
- **Метод:** каждый этап начинается с чистой базы и добавляет одно изменение. Запросы уходят строго по расписанию (open-loop), время считается от момента, когда запрос *должен был* уйти. Запрос дольше 1 с считается ошибкой.
- **Запуск:**
  - `bash run.sh` — 5 основных этапов, результаты в `results/summary.csv`;
  - `bash experiments.sh` — дополнительные эксперименты, результаты в `results/*.txt` и `results/experiments.csv`.

## 1. Индексы + EXPLAIN ANALYZE

### Какие индексы добавили (`sql/03_indexes.sql`)

| Индекс | Для какого запроса |
|---|---|
| `products_category (category_id, id) WHERE status = 'active'` | страница категории |
| `products_category_price (category_id, price) WHERE status = 'active'` | фильтр по категории и цене |
| `outbox_pending (id) WHERE processed_at IS NULL` | outbox-воркер |

**Правило составного индекса:** сначала колонка с `=` (категория), потом колонка с диапазоном или сортировкой. `WHERE status = 'active'` делает индекс partial: удалённых товаров в нём нет, и он меньше.

### EXPLAIN ANALYZE: до и после (`results/baseline-explain.txt`, `results/indexed-explain.txt`)

| Запрос | До | После |
|---|---|---|
| `list_filter` (категория 100, цена 100–110) | `Parallel Index Scan using products_pkey`, **Rows Removed by Filter: 333 258** × 3 процесса, 23 620 страниц, **117 мс** | `Bitmap Index Scan on products_category_price`, 39 строк, 45 страниц, **0.24 мс** |
| `list_category`, маленькая категория | `Index Scan using products_pkey`, отбросил 3 431 строку, 0.60 мс | `Index Scan using products_category`, отбросил 0, **0.08 мс** |
| `list_category`, большая категория | по PK, отбросил 315 строк, 0.09 мс | **тот же план**: планировщик решил, что так дешевле |
| `get` | `Index Scan using products_pkey`, 0.07 мс | без изменений, уже оптимум |
| outbox-воркер | `Parallel Seq Scan`, перебор 3 млн строк, 52 мс | `Index Scan using outbox_pending`, **0.008 мс** |

### Объяснение

- **Почему было медленно.** Индекса по категории и цене не было. Postgres шёл по всем товарам подряд и у каждого проверял условие. Подходящих ~40 на миллион, поэтому он перебрал почти всю таблицу ради 20 строк.
- **Почему стало быстро.** Индекс сразу прыгает к «категория 100, цена 100», читает до «цена 110» и находит ровно 39 строк. Работы стало в ~500 раз меньше.
- **Почему под нагрузкой ускорился даже `get`, хотя его план не менялся.** Медленные фильтры занимали все 80 соединений, и быстрые запросы стояли за ними в очереди. На 2000 RPS p99 `get` был 998 мс, а стал 1.4 мс. Один плохой запрос тормозит всю базу.

## 2. Цена индексов: что стало быстрее, что медленнее

Файлы: `results/index-cost.txt`, `results/experiments.csv`. Одна и та же база до и после `03_indexes.sql`.

| | Без своих индексов (2 индекса) | С индексами (4 индекса) | Изменение |
|---|---|---|---|
| **Чтение** `list_filter` | 117 мс | 0.24 мс | **в ~480 раз быстрее** |
| **Чтение** p99 при 2000 RPS | ~1000 мс, 12 519 ошибок | ≤ 2.9 мс, 0 ошибок | быстрее |
| INSERT 100 000 товаров | 1 065 мс | 1 393 мс | **+31% медленнее** |
| UPDATE цены у 100 000 товаров | 856 мс | 1 369 мс | **+60% медленнее** |
| Только запись, 1000/с: p50 / p99 | 5.2 / 53.6 мс | 5.5 / 609 мс | хвост задержки сильно вырос |
| Размер индексов `products` | 72 МБ | 145 МБ | **+73 МБ** (+44% от таблицы в 166 МБ) |
| Построить индексы | — | 425 + 581 мс (+136 мс на `outbox_pending`) | разовая цена |

### Объяснение

- **Чтение** стало быстрее в сотни раз: это ради чего индексы и ставили.
- **INSERT медленнее на 31%:** каждая новая строка теперь пишется в 4 индекса, а не в 2.
- **UPDATE цены медленнее на 60%, сильнее, чем INSERT.** Цена теперь входит в индекс `products_category_price`. Postgres не может обновить строку «на месте» (HOT update) и вынужден добавлять запись во **все** индексы таблицы. UPDATE, который не трогает колонки из индексов (например, описание), остался бы дешёвым.
- **Тест «только запись»** шёл на загруженной машине (параллельно работали тесты другого проекта), поэтому абсолютные цифры шумные. Направление при этом одно во всех повторах: с индексами хвост задержки записи растёт.
- **Вывод.** У нас чтений в ~500 раз больше, чем записей, поэтому индексы окупаются. Но каждый индекс должен быть нужен конкретному запросу: лишний индекс замедляет каждую запись и занимает место.

## 3. Партиционирование: нужно ли и какое (день / неделя / месяц)

### Нужно ли вообще

| Таблица | Партиционировать? | Почему |
|---|---|---|
| `products` | **нет** | 1 млн строк для Postgres — немного. Товары ищут по `id`: при партициях по категории поиск по id шёл бы во все партиции |
| `outbox` | **да** | журнал, растёт без конца: при 20 записях/с это **1.73 млн событий в день, ~52 млн в месяц**. Старое не нужно, и его надо регулярно удалять |

### Какое: сравнили день / неделю / месяц (`results/partition-granularity.txt`)

Одни и те же 3 млн событий за 90 дней разложены по-разному. Время — второй (тёплый) запуск, планирование + выполнение.

| | Без партиций | Месяц | Неделя | День |
|---|---|---|---|---|
| Партиций (на 90 дней) | 0 | 5 | 15 | 92 |
| Запрос воркера за 7 дней | 0.03 + 0.005 мс | 0.12 + 0.01 мс, отсечено 3 | 0.28 + 0.02 мс, отсечено 12 | **1.63** + 0.05 мс, отсечено 83 |
| Тот же запрос без окна (все партиции) | 0.02 + 0.003 мс | 0.06 + 0.01 мс | 0.22 + 0.03 мс | **1.10 + 0.19 мс** |
| Найти событие по id (все партиции) | 0.01 + 0.006 мс | 0.05 + 0.02 мс | 0.13 + 0.06 мс | **0.91 + 0.33 мс** |
| Вставка 3 млн | 16.1 с | 14.0 с | 13.3 с | 16.6 с |

**Что видно:**
- **Отсечение партиций работает всегда** (`Subplans Removed`). Но Postgres всё равно **планирует запрос по всем партициям**: окно `now() - 7 days` известно только при выполнении. Поэтому чем больше партиций, тем дороже каждый запрос: 92 дневные партиции дают ~1.6 мс одного только планирования, в 13 раз больше, чем месячные.
- **Запросы без ключа партиции** (поиск по id) ходят во все партиции: на 92 партициях это в ~17 раз медленнее, чем на 5.
- **Скорость вставки** почти одинаковая: разброс 13–17 с — это шум, а не цена партиций.

### Что выбрали и почему

Решает **срок хранения** (retention). Обработанное событие outbox нужно только для отладки и повторной отправки, храним **7 дней**. Удалять можно только партицию целиком, поэтому реально хранится «7 дней + размер одной партиции».

| | Месяц | Неделя | День |
|---|---|---|---|
| Сколько данных лежит при хранении 7 дней | до ~38 дней ≈ **66 млн строк** | до 14 дней ≈ 24 млн | **8 дней ≈ 14 млн** |
| Сколько партиций живёт одновременно | 2–3 | 3–4 | ~9–10 |
| Планирование запроса воркера | ~0.1 мс | ~0.3 мс | ~0.3 мс (как неделя: партиций ~10, а не 92) |
| Один `DROP` удаляет | ~52 млн строк | ~12 млн | ~1.7 млн |

**Выбор: дневные партиции при хранении 7 дней.** Таблица в ~5 раз меньше, чем при месячных, а партиций живёт всего ~10, поэтому планирование остаётся дешёвым.

Правило из эксперимента: **живых партиций должно быть десятки, а не сотни.** Если бы хранили 90 дней, дневные партиции дали бы 92 штуки и дорогое планирование. Тогда правильным выбором была бы неделя.

*В основных этапах (`run.sh`) стоят месячные партиции, потому что seed хранит 90 дней истории. На чтения товаров это не влияет, `outbox` они не трогают. Перейти на дни — это смена `'1 month'` на `'1 day'` в `04_partitioning.sql` плюс ежедневный DROP.*

## 4. Удаление старых данных: DELETE или DROP PARTITION

Файлы: `results/delete-vs-drop.txt`, `results/*-retention.txt`. Удаляли самый старый месяц: 71 930 событий из 3 млн, по-настоящему, с COMMIT.

| | `DELETE` (обычная таблица) | `DROP` партиции |
|---|---|---|
| Время | **175 мс** + VACUUM потом **481 мс** | **6.3 мс** |
| Записано в WAL (и потом передано на реплику) | 9.9 МБ | 1.0 МБ |
| Размер таблицы после | 362 → 362 МБ (**не уменьшилась**, даже после VACUUM) | 356 → 348 МБ (место освобождено сразу) |
| Мёртвые строки | 71 930, нужен VACUUM | нет |
| Удалить события **одного товара** (`product_id = 42`) | 115 мс — **работает** | **невозможно**: DROP удаляет только целую партицию; DELETE по партициям — 113 мс |

### Где что выигрывает

- **DROP выигрывает при удалении по времени** (retention): он не зависит от объёма, почти не пишет WAL, сразу освобождает диск, не оставляет работы для VACUUM. При реальном объёме (1.7 млн событий в день) DELETE работал бы секунды и плодил гигабайты мёртвых строк.
- **DELETE выигрывает, когда:**
  - условие не совпадает с ключом партиции: удалить данные одного товара или пользователя, исправить ошибочные записи;
  - данных мало, и партиции не нужны вовсе;
  - нужна обычная транзакция: `RETURNING`, триггеры, каскадные внешние ключи.
- **Вывод:** retention старых событий делаем через `DROP` партиций по расписанию, а точечные удаления — через `DELETE`.

## 5. PgBouncer: зачем и что дал

| Тест | Соединений у клиента | Соединений у Postgres | p99 `get` | Ошибки |
|---|---|---|---|---|
| напрямую | 85 | 85 | 1.4–2.2 мс | 0 |
| PgBouncer, 500 / 1000 / 2000 RPS | 85 | **5 / 7 / 13** | 1.1–1.8 мс | 0 |
| **300 клиентов напрямую** | 300 | — | — | `sorry, too many clients already` |
| **300 клиентов через PgBouncer** | 305 | **14** | 1.1 мс | **0** |

### Объяснение

- **Зачем.** Каждое соединение с Postgres — отдельный процесс, а лимит `max_connections = 100`. Подов много, у каждого свой пул: 20 подов × 10 соединений = 200 > 100. Напрямую 300 клиентов получают ошибку.
- **Как работает.** В режиме `transaction` PgBouncer выдаёт настоящее соединение только на время одной транзакции. Лишние клиенты ждут в очереди, а не получают ошибку.
- **Закон Литтла:** нужно соединений = RPS × время запроса ≈ 1000 × 1 мс ≈ 1–2. Поэтому соединений у Postgres растёт с нагрузкой (5 → 7 → 13), а не с числом клиентов: 300 клиентов → 14 соединений.
- **Что дал:** сотни клиентов вместо ошибки и в 6–20 раз меньше процессов у базы. **Запросы не ускорил**, p99 тот же.
- **Почему пул 20, а не 300:** больше 100 Postgres не даст, а 300 одновременных запросов на 12 потоках CPU только мешают друг другу.

## 6. Реплика: нужна или нет, с репликой и без

### Сравнение 1: обычная машина (`results/summary.csv`, этапы `pooled` и `replica`)

| 2000 RPS | Без реплики | С репликой |
|---|---|---|
| p99 `get` / `list_filter` / `write` | 1.4 / 2.5 / 2.6 мс | 1.4 / 2.9 / 3.7 мс |
| Соединений у primary | 13 | **1** |

Primary не перегружен (12 потоков CPU), поэтому реплика скорость не меняет. Она только снимает чтения с primary.

### Сравнение 2: primary и реплика по 0.5 CPU, как два маленьких сервера (`results/experiments.csv`, `results/replica-cpu.csv`)

Чтения 1000 или 2000 RPS плюс запись 200/с. Без реплики всё идёт на primary, с репликой чтения идут на реплику.

| | Без реплики, 1000 | С репликой, 1000 | Без реплики, 2000 | С репликой, 2000 |
|---|---|---|---|---|
| Загрузка CPU primary (лимит 50%) | 27% | 9% | **51% — упёрся в лимит** | **10%** |
| Загрузка CPU реплики | 5% | 26% | 3% | 41% |
| Ошибки (таймаут 1 с) | 0 | 0 | **41 583** (из них 5 301 — запись) | **0** |
| p99 чтений | 3–26 мс | 168–258 мс | ~1000 мс | **47–65 мс** |
| p99 записи | 443 мс | 548 мс | ~1000 мс | 794 мс |

### Объяснение

- **На 2000 RPS реплика спасает систему.** Один сервер упирается в CPU и падает: 41 тыс. ошибок, причём не проходит даже **запись**. С репликой чтения уходят на второй сервер, primary загружен на 10%, ошибок 0. Это повторилось во всех четырёх прогонах.
- **На 1000 RPS реплика не помогает.** Primary справляется сам (27% при лимите 50%), а с репликой p99 даже хуже. Лимит в 0.5 CPU даёт всплески задержки при обработке (cgroup throttling), а на машине параллельно шли чужие тесты. Поэтому абсолютные p99 в этом сравнении шумные, а надёжные цифры — загрузка CPU и ошибки.
- **Цена реплики — лаг:** 0.7 мс в обычном режиме, до 222 мс при массовой загрузке (`results/replica-lag.txt`). Поэтому с реплики читаем только то, что терпит задержку: карточку и каталог, но не проверку перед записью.

### Нужна ли реплика нам

**Да, одна асинхронная, но не ради скорости:**
1. **Запас мощности на случай, когда кэш холодный или упал.** Тогда до базы доходит не 1000, а 2000+ RPS, и один сервер падает (сравнение 2).
2. **Отказоустойчивость.** Если primary умрёт, реплику повышаем до primary. Потерять можно ≈ лаг, то есть меньше 1 мс данных.
3. **Чтения не мешают записи:** primary держит 1 соединение и ~10% CPU.

При обычной нагрузке (~1000 RPS) и нормальном сервере один primary справляется сам, и разницы в скорости нет.

## 7. Самый медленный запрос, который индексом не решить: флаг или watermark

Файл: `results/flag-vs-watermark.txt`. В `outbox` 3 млн отправленных событий плюс очередь из 100 000 новых.

### Какой запрос

Самый медленный запрос на `outbox` — это **воркер, который ищет неотправленные события**: `WHERE processed_at IS NULL ORDER BY id LIMIT 100`. Без индекса он перебирает все 3 млн строк: **338 мс, Rows Removed by Filter: 3 000 000**.

Обычный индекс это не решает. Индекс по `processed_at` содержал бы все 3 млн строк, а значение флага меняется у **каждого** события после отправки, то есть индекс переписывается на каждой записи. Partial-индекс ускоряет чтение, но не убирает главную цену флага: `UPDATE` на каждое событие.

### Два способа

- **Флаг:** после отправки каждое событие помечаем `UPDATE ... SET processed_at = now()`, воркер ищет `processed_at IS NULL`.
- **Watermark:** события не трогаем, храним одно число — id последнего отправленного (таблица `outbox_watermark`). Воркер читает `WHERE id > :watermark ORDER BY id LIMIT 100` по первичному ключу и после пачки обновляет одну строку.

### Результаты

| | Флаг без индекса | Флаг + partial-индекс | **Watermark** |
|---|---|---|---|
| Запрос воркера | **338 мс** | 0.041 мс | **0.038 мс** (по PK, отдельный индекс не нужен) |
| Отправить 100 000 событий пачками по 100 | — | 4.6 с | **2.2 с** |
| Записано в WAL | — | **29 МБ** | **112 КБ** (в ~260 раз меньше) |
| Рост таблицы | — | +8.4 МБ (мёртвые версии строк) | **0** |
| UPDATE на пачку из 100 | — | 100 строк + индексы | 1 строка |

### Что выбрали: watermark

- **Чтение** такое же быстрое, как с partial-индексом, но отдельный индекс не нужен.
- **Запись в 2 раза быстрее**, WAL в ~260 раз меньше. Реплике тоже не надо проигрывать 29 МБ изменений.
- **Таблица только пополняется** и никогда не обновляется. Поэтому старые партиции не трогаются после заполнения и удаляются `DROP` без мёртвых строк и VACUUM (пункты 3–4).
- **Риск, и как его закрыть.** id выдаются при вставке, а не при коммите. Транзакция с id 100 может закоммититься позже, чем id 101, и watermark её пропустит. Закрывается одним из способов:
  - читать только события старше нескольких секунд (`created_at < now() - interval '5 seconds'`);
  - один писатель;
  - позиция в WAL (LSN) вместо id, как делает CDC. Это тема SIS-4.

| Watermark вместо флага | WAL в 260 раз меньше, запись в 2 раза быстрее, таблица append-only | риск пропуска событий, нужен запас по времени или LSN |

## Ограничения

- Всё работает на одной машине (12 потоков, 15 ГБ RAM): primary, реплика, PgBouncer и генератор нагрузки делят один CPU и один диск.
- Пока шли дополнительные эксперименты (пункты 2, 3, 6, 7), на машине параллельно работали тесты другого проекта. Поэтому абсолютные задержки там шумные. Выводы опираются на то, что повторялось: время SQL, WAL, размеры, загрузку CPU и число ошибок.
- Генератор нагрузки на Python держит расписание до ~2000 RPS, поэтому выше не мерили.
- Меряли SQL напрямую, без HTTP API и Redis из SIS-2.
- Настройки Postgres по умолчанию (`shared_buffers = 128MB`), чтобы выигрыш каждого шага шёл от одного изменения.
